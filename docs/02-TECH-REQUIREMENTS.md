# 02 — Technical Requirements

## 1. Runtime

- Node.js 22+.
- TypeScript strict mode.
- Next.js frontend.
- Node.js/Express backend.
- MongoDB Atlas.
- Mastra integrated into the backend/AI service.
- Ollama for local Gemma development.
- ElevenLabs accessed server-side only.

## 2. Functional requirements

### FR-001 Authentication — Clerk
Authentication is delegated to Clerk. The application must not implement password storage, session issuance, or OAuth credential handling itself.

- Next.js uses `@clerk/nextjs` with `ClerkProvider` and `clerkMiddleware()`.
- Express uses `@clerk/express` middleware to validate the Clerk session and expose authenticated identity to routes.
- The canonical application identity is `clerkUserId` from Clerk.
- The MongoDB `users` collection stores the local application profile keyed by `clerkUserId`.
- Protected API resources derive identity from the verified Clerk session; never trust a client-supplied `userId`.
- Sign-in/sign-up UI uses Clerk's components/customizable flows while preserving the ExploBook visual theme.

### FR-002 Reader profile
System stores genres, goals, difficulty, preferred length, available reading time and evolving Reader DNA.

### FR-003 Book grounding
Every recommendation must reference a `bookId` that exists in the catalogue. Gemma cannot invent a final book record.

### FR-004 Recommendation
System retrieves candidates, applies deterministic filters, asks Gemma to rank/explain candidates, validates structured output, and stores the recommendation.

### FR-005 Voice
User can request a short spoken recommendation preview. ElevenLabs API keys never reach the browser.

### FR-006 Reading session
Start creates a session. Timer is based on server timestamps, not browser tick count. Stop calculates duration from timestamps.

### FR-007 Reflection
Completed sessions can collect rating, difficulty, favorite aspect, moral/meaning response, recommendation intent and vocabulary.

### FR-008 Analysis
Gemma returns structured analysis. Analysis must never change deterministic XP directly without passing through the scoring engine.

### FR-009 Orb
Exactly one Orb is created for each completed book cycle. Reprocessing must be idempotent.

### FR-010 Progression
XP, level, streak and statistics update transactionally/idempotently.

### FR-011 History
Users can view completed books, reading sessions, reflections, XP and Orbs.

### FR-012 Search/purchase links
Optional SerpApi integration may provide current discovery/purchase links. Links must be treated as external and never as payment flows.

## 3. Non-functional requirements

- Type-safe request/response schemas using Zod.
- Server-side validation for every mutation.
- Authentication/authorization on all user-owned resources.
- No secret keys in client bundles.
- Structured AI output with schema validation.
- AI failures degrade gracefully to deterministic recommendations or a clear retry state.
- Reading timer survives tab refresh/reconnect by deriving elapsed time from timestamps.
- Recommendation requests are idempotent where possible.
- API responses have stable error shapes.
- AI operations have request IDs and tracing.
- All external calls have timeout and retry policies appropriate to the provider.
- Automated tests for scoring and recommendation contracts.

## 4. AI reliability requirements

1. Gemma never creates final book IDs.
2. Gemma must return JSON conforming to the specified schema.
3. Invalid JSON is rejected and optionally retried once with a repair prompt.
4. Recommendation candidates are generated by application code/vector search first.
5. Deterministic ranking factors are computed by application code.
6. Gemma supplies semantic ranking/explanation within the provided candidate set.
7. User review text is treated as untrusted content, not as instructions.
8. AI output is stored with model/version metadata.
